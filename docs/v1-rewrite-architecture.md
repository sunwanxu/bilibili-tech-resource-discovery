# v1 重写架构基线

状态：设计基线（2026-08-15）。本文件描述 v1 的目标与边界，不改变现行 v0.8 Skill。

## 1. 产品目标

v1 只解决一个主问题：用户用自然语言描述需求后，系统从 B 站找到值得看的技术视频，
并从视频简介、字幕、评论以及相关页面中挖掘可用的代码、PCB、文档和项目资料。

它有两种明确模式：

- `learning`：优先判断讲解质量、难度、知识递进、演示完整性和用户水平适配。
- `resource`：优先扩大 B 站候选覆盖，再验证视频周边的源码、硬件文件和授权证据。

混合需求先询问用户更看重哪一种。用户不愿继续说明时，使用稳定默认值，不阻塞搜索。

## 2. 用户流程

首次使用最多逐步询问三个问题，而不是一次展示配置表：

1. 你最终想学会什么，或想拿到什么可用资料？
2. 你目前做到哪一步、看得懂什么程度？
3. 你更想快速精选、标准搜索，还是尽量全面？

随后按需询问：

- 是否允许打开独立的 B 站登录窗口。登录通常能提高字幕、评论和受限页面覆盖；拒绝后仍可使用公开模式。
- 只验证核心结果还是验证全部结果。默认核心验证。
- 是否配置 Firecrawl、模型 API 等可选服务。拒绝后核心链路仍必须可用。
- 是否保留完整字幕和评论。默认最小化保存。

## 3. 十二阶段流水线

每个阶段都只有结构化输入和输出，可以被独立替换、缓存和测试。

| 阶段 | 职责 | 默认网络行为 |
|---|---|---|
| 1. Intent | 识别学习/资源模式、用户水平、约束和验证范围 | 无 |
| 2. Setup | Windows 安装、升级、自检和修复 | 仅安装/升级时 |
| 3. Session | 独立可见浏览器登录、会话检查、公开模式 | 用户同意后 |
| 4. Query plan | 生成少量高信息量查询，保留型号、年份、题号和短语 | 无 |
| 5. Bilibili discovery | 从 B 站搜索页面获得大批视频候选 | 默认 1 个精确查询，必要时渐进增加 |
| 6. Evidence expansion | 对高价值候选按需扩展 UP、合集、相关文章和相关视频 | 只扩展高价值分支 |
| 7. Normalize/rank | 统一 BV/AV/URL、去重、相关性和多样性排序 | 无 |
| 8. Video reading | 读取简介、字幕、有限评论和必要元数据 | 只读取候选子集 |
| 9. Link mining | 从所有证据中提取并归并外部资源线索 | 无额外请求 |
| 10. Resource verification | 验证仓库、文件、访问状态、完整性和许可证作用域 | 核心或全部验证 |
| 11. Report | 生成稳定 JSON 与面向人的精选结果/完整候选池 | 无 |
| 12. Runtime control | SQLite 缓存、断点、预算、熔断、事件时间线 | 横切控制 |

## 4. 搜索主路

### 4.1 默认策略

默认使用项目托管的可见 Edge/Chromium 会话打开 B 站搜索结果页，以普通用户可见页面为证据来源。
一次查询尽量读取一整页候选，再在本地筛选；候选不足时才发第二条查询。系统不复制日常浏览器
Cookie 数据库，不依赖 DPAPI、Firefox 或 Cookie 导出插件。

搜索量不再等同于请求量。候选广度主要来自：

- 一页搜索结果中的全部有效候选；
- 本地缓存中的历史候选；
- 高价值视频的相关视频、UP 投稿、合集和关联文章；
- 可选的公开网页索引补充，但它必须明确标记来源，不能伪装成 B 站内部搜索。

### 4.2 风控原则

- 一次运行设定明确的 B 站请求预算，而不是固定执行八条查询。
- 查询按需渐进；候选达到目标后立即停止继续搜索。
- HTTP 412 是服务端风险控制信号。出现后停止本轮所有新的 B 站请求，但继续处理缓存和已经取得的证据。
- 412 不自动重试、不换账号、不使用代理规避，也不把本地冷却描述成 B 站官方倒计时。
- 运行结果区分 `success`、`partial_success`、`failed`，并区分执行失败与熔断跳过。

## 5. 证据与排序

### 5.1 两阶段排序

先进行便宜的候选排序，再对少量候选深读：

1. 标题、摘要、作者、发布时间、查询命中、来源多样性和缓存证据形成候选分。
2. 简介、字幕、评论和外链形成证据分。

候选不会因为一个脆弱过滤器而“全部拒绝后全部捞回”。过滤只排除明确无关或无效项；其余候选
保留分数与原因，交给多样性排序。显式提供的视频链接永不经过主题硬过滤。

### 5.2 模式差异

- 学习模式：讲解清晰度、难度适配、演示和课程递进权重更高。
- 资源模式：外链证据、文件完整性、可复现性、访问状态和授权范围权重更高。

宿主 AI 可以参与需求理解和最终评价，但网络访问、缓存、证据来源和验证结论必须由确定性引擎记录。

## 6. 开源证据标签

项目级结论不得高于关键组成部分中证据最弱的一档：

1. `verified_license`：仓库或资源存在，许可证已读取且作用域明确。
2. `public_source_no_license`：源码公开，但没有可验证许可证。
3. `claimed_open_no_link`：作者声称开源，但尚未找到可访问链接。
4. `downloadable_authorization_unclear`：文件可下载，授权范围不明。
5. `login_or_manual_access`：链接有价值，但需要登录、群聊、网盘提取码或人工操作。
6. `dead_link`：证据存在但链接已失效。
7. `no_open_source_evidence`：检查过的证据中没有开源线索。

单个 GPL 组件不能让完整项目自动变成“GPL 项目”。报告必须记录许可证对应的具体资源和范围。

## 7. 数据与隐私

- SQLite 保存标准化候选、证据哈希、验证结果、运行事件和断点。
- 默认不保存媒体直链、请求头、Cookie、评论作者身份或完整提取器原始响应。
- 默认报告保存摘要和必要证据片段；完整字幕/评论只能在用户同意后保留。
- 每完成一个深读或验证步骤就写入 checkpoint，单个坏 URL 或进程中断不会丢掉整轮结果。
- Markdown 只由 UTF-8 JSON 派生；CLI 固定输出 `latest.json` 指针和机器可读摘要。

## 8. Windows 安装目标

发布物提供两个入口：

- 用户双击安装包：自动安装隔离运行时、Skill、浏览器依赖并完成离线自检。
- 用户把 GitHub 地址交给 AI：AI 调用同一个非交互安装入口。

安装不要求用户预装 Python、Firefox、Cookie 插件，也不使用 editable install。运行时版本锁定，升级先
安装到新目录并自检，通过后原子切换；旧版本保留用于回滚。首次真正需要登录时才打开独立可见窗口。

## 9. 对外边界

核心是独立搜索引擎，Skill 只是自然语言交互和编排层。Codex、OpenCode、未来网站或浏览器插件都调用
同一稳定 JSON 协议，不能各自复制搜索逻辑。外部服务、模型、Firecrawl 和 OpenCLI 都只能是可选适配器。
